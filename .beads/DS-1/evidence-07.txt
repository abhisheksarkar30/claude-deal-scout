--------------------------------------------------------------------------------
H1 — does a subagent's `tools:` frontmatter accept `mcp__claude-in-chrome__*`
     names, and does it actually restrict the agent?
--------------------------------------------------------------------------------
Why it matters: `tools:` is supposed to be an independent second layer beneath
the guard — the guard is default-deny for tools it MATCHES, but a tool name the
hook's matcher never sees is a silent gap (R9). If `tools:` does not restrict,
the guard is the ONLY layer, and any claim of "two independent layers" is false.
The plan explicitly forbids describing one layer as two (R1/R3).

Procedure (needs the user's Chrome — ASK FIRST)
  1. Install the plugin from this repo as a local directory marketplace.
  2. Spawn the `claude-deal-scout:deal-scout` subagent with a trivial requirement.
  3. Confirm from the transcript that it actually has the Chrome tools it needs.
  4. Then confirm the negative: that a tool OUTSIDE the seven is not available to
     it. The cleanest probe is to ask the subagent to call, say, `read_network_requests`
     or `javascript_tool` — it should not have the tool at all.

Pass  : the subagent can call the seven, and cannot call anything else.
Fail  : it can call a tool outside the seven (the list was ignored or widened).

If it FAILS:
  - The `tools:` allowlist is NOT a second layer. Say so plainly in Review Notes
    and in docs/SECURITY.md (br-DS-1-08), and remove any prose implying two.
  - The guard's default-deny is then the SOLE control (br-DS-1-03), which makes
    H4's matcher coverage — that every denied tool name is matched by
    `mcp__(claude-in-chrome|Claude_Browser)__.*` — load-bearing rather than
    defence-in-depth. Treat an H4 failure as a blocker, not a note.

--------------------------------------------------------------------------------
H2 (reconfirmation) — does a `navigate` inside the subagent expose the final URL?
--------------------------------------------------------------------------------
br-DS-1-03's evidence-03.txt owns the primary check. Reconfirm it here
specifically from INSIDE the subagent, because that is the path the `post` hook
actually guards: the hook fires on the subagent's tool call, not on a main-thread
one.

Procedure: with the subagent running, have it `navigate` to an allowlisted URL
that redirects, and inspect the tool response it gets back. Confirm the response
carries the URL the browser actually landed on, reachable by `collectUrls` in
scripts/guard.js.

If it FAILS: the post-navigation layer is inert for the subagent path too. Same
consequence and same caveat as evidence-03.txt — the pre-check and the agent's
"discard and close" instruction are then the only redirect controls.
