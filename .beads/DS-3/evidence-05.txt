H6 — does an amazon.in /dp/<ASIN> page expose, as text and with no click: the brand
     attribute, a brand-storefront link, a "Sold by" seller name, and an inline
     top-review list carrying verified-purchase badges and star values?
--------------------------------------------------------------------------------
RESULT: **NOT RUN. Open.** Two independent reasons, both worth recording:

1. robots.txt (fetched 2026-10-11, HTTP 200, 9320 bytes). For `User-agent: *` the product path is
   NOT disallowed — only `/dp/product-availability/` and `/dp/rate-this-item/` are. BUT the file
   then enumerates automated agents with a blanket `Disallow: /`, and **`ClaudeBot` is on that
   list**, alongside GPTBot, CCBot, PerplexityBot, Google-Extended, GoogleAgent-Mariner,
   GoogleAgent-Shopping, meta-externalagent, Bytespider, Scrapy, PetalBot, Devin, AI2Bot,
   Gemini-Deep-Research, MistralAI-User, Diffbot, Copilot and others. Reading an amazon.in product
   page as an automated Claude agent is therefore against the site's stated policy, and getting
   past it would mean presenting a browser User-Agent while not being one. That is the workaround
   the DS-1 survey explicitly refused ("respect bot signals"; a robots-disallowed source is a "no",
   not a workaround), so it was not attempted.

2. Independently, an honest-UA GET is blocked anyway. `GET https://www.amazon.in/dp/B0CX23V2ZK`
   (plain curl UA) → **HTTP 503**, 3793 bytes, an anti-bot interstitial:
     title: "Amazon.in"
     text:  "Amazon.in Click the button below to continue shopping Continue shopping"
   That is the interstitial class the agent's own rules already say to stop at and report as
   `blocked`. There is no product data in the response — no title, price, rating, seller or brand.

CONSEQUENCE, stated plainly: none of H6's four claims (brand attribute, brand-storefront link,
"Sold by" seller, inline review list with verified-purchase badges and star values) is confirmed or
refuted. The plan's §3.5 extraction assumes all four; that assumption is **untested**. It is not
contradicted — a real browser session renders all of this normally, which is precisely how the
plugin is designed to read amazon.in, and why the shipped adapter drives a session rather than
crawling. But "the design assumes a browser session" is not the same as "verified", and this file
will not pretend otherwise.

H7 — does a flipkart /<slug>/p/<id> page expose the seller name and the brand
     attribute WITHOUT a click?
--------------------------------------------------------------------------------
Judged on the RAW SERVER HTML — the same bytes a browser receives before it runs JavaScript, but
NOT the rendered DOM. Read via `curl` (plain UA, HTTP 200, 1 243 333 bytes) of a real product URL
taken from Flipkart's own product sitemap (`sitemap_pp_product_sitemap_v2_2.xml.gz`, listed in its
robots.txt):

  https://www.flipkart.com/wraparts-wrap-arts-pooja-treat-hamper-ideal-gift-festivals-housewarmings-etc-ceramic-brass-glass/p/itm000439652e07f

The page is server-rendered, not a bare JS shell: it carries `window.__INITIAL_STATE__` (5
occurrences) and 23 `<script>` tags, and its `<title>` is the real product name.

  BRAND ATTRIBUTE      **YES, present in the raw HTML.**
                       `…"ratingsCount":0,"reviewsCount":0},"bd":"wraparts","pas":{…`
                       The `bd` key in the product's SSR state carries the brand, `wraparts`.
                       So H7's brand half is CONFIRMED at the HTTP level.
  RATING + COUNTS      **YES, present in the raw HTML.**
                       `"pr":{"individualRatingsCount":[{"ratingValue":1,"ratingCount":0},…],
                       "rating":0,"ratingsCount":0,"reviewsCount":0}`
                       All zero here because this listing genuinely has no ratings — the point is
                       that the fields are in the initial payload.
  PRICE / MRP          present: `"ppd":{"fsp":2533,"finalPrice":2533,"mrp":5000,…}`.
  SELLER NAME          **NOT in the raw HTML.** No `sellerName`, no `"seller"` key, no "Sold by".
                       Every `seller` occurrence is chrome, not the seller's name:
                         - `href="https://seller.flipkart.com/sell-online/…" title="Become a Seller"`
                         - `href="/sellers?pid=PJTHERJGTJQRRBT8"` (a link, not a name)
                         - the text "See other sellers"
                       The presence of that `/sellers?pid=…` link means an offer/seller panel
                       exists on the page — so the rendered DOM very likely DOES show the seller
                       name. **UNVERIFIED either way.** It is not refuted; it is unread.
  REVIEW BADGES        "Verified Purchase" and "verified" do not appear in the raw HTML.
                       Consistent with §9 (Flipkart reviews are click-gated and out of scope) and
                       with its robots.txt, which disallows `/reviews/`, `*/product-reviews/*`,
                       `*/ratings-reviews-details-page`, `*/write-review/*` and `/search?`. Note
                       that `*/sellers?*` and `*/seller-details?*` are disallowed too, so the
                       seller *page* is off-limits — only a seller name printed on the product page
                       would be fair game.

H7 VERDICT: **brand half CONFIRMED (raw HTML); seller-name half UNVERIFIED** — it needs the
rendered DOM, which this session could not produce. Per the bead, a `null`/absent result is an
expected outcome, not a failure: Flipkart's client rendering is already recorded at
`sites/flipkart.json:20`. The step-3 prompt rule stands as written — if the seller is not printed,
omit `seller`; a missing `seller` costs one support on the ladder and `no_brand_store` /
`review_sample_too_small` report the rest.

H8 — br-DS-3-05: does SOME third-party review source pass all three of an addressable
     lookup, a rating/count readable as text without a click, and a permitting robots.txt?
================================================================================
STATUS: **SURVEY RUN 2026-10-11 at the HTTP/robots level. DECISION: SHIP NO `review` ADAPTER.**
Same browser-pane limitation as H6/H7 above, so the rendered-text half is unverified — but here the
blockers are mostly decisive on their own. No User-Agent spoofing: every fetch is a plain `curl`.

The rule being applied, from the plan and the DS-1 precedent: a source qualifies only if a lookup can
be **built from a product's public URL or title** (the agent cannot type into a form and cannot click),
its **rating/count are exposed as text without a click**, and its **robots.txt permits** the read. A
robots-disallowed or bot-blocked source is a "no", not a workaround.

CANDIDATE 1 — gsmarena.com (phone reviews; URL-shape `/<brand>_<model>-<id>.php`)
  robots.txt: HTTP 200, 2053 bytes. **DISQUALIFIED.** It carries a blanket `Disallow: /` for
  `GPTBot`, **`ClaudeBot`**, `CCBot` and **`anthropic-ai`**. Reading it as this agent is against the
  site's stated policy, exactly as for amazon.in in H6. Also fails requirement 1 independently: the
  `-<id>` in the URL is site-internal, so the lookup is not constructible from a title.

CANDIDATE 2 — trustpilot.com
  robots.txt: HTTP 200, 25101 bytes. **DISQUALIFIED, twice over.** It lists `anthropic-ai` (and
  `Applebot-Extended`, `ImagesiftBot`, `Omgilibot`, `Yandex`, …) among its disallows; and it indexes
  **businesses by domain, not products**, so there is no product-level lookup to build at all.

CANDIDATE 3 — mouthshut.com (India-specific product reviews)
  **EXCLUDED — unreachable.** `curl` gets a connection reset (`Recv failure: Connection was reset`,
  HTTP 000) for its robots.txt; no response was obtained. Treated the same way DS-1 treated
  smartprix's 403: respect the signal, do not probe around it.

CANDIDATE 4 — 91mobiles.com (India; prices, specs and user ratings; URL shape
              `/<brand>-<model>-price-in-india`)
  robots.txt: HTTP 200, 3553 bytes. **PERMITTED for a generic agent** — no AI-agent block at all
  (the only blanket `Disallow: /` entries are for `008` and `Baiduspider`). Product and price pages
  are not disallowed; what IS disallowed is `/forum/`, `/answers/`, `/video/`, `/api_mobile`,
  `/directory/`, `/articles/`, `/photos/` and `/*viewReviewComments`.
  **BUT every constructed lookup returned HTTP 403**, a uniform 5486-byte bot-block page:
    /samsung-galaxy-s24-price-in-india        -> 403
    /samsung-galaxy-s24-ultra-price-in-india  -> 403
    /apple-iphone-15-price-in-india           -> 403
  So requirement 1 could not be confirmed. **This one is different in kind from candidates 1–2**: its
  robots.txt *permits* the read and the 403 is a plain-`curl` user-agent block, not a stated policy.
  In a real browser pane it would very likely serve normally. It is therefore **not rejected on
  policy grounds** — it is unverified because the browser pane was unavailable, and it is the one
  candidate still worth a rendered-page check.

DECISION: **ship NO `sites/<review-site>.json`.** Two reasons, in order:
  1. No candidate cleared all three requirements on the evidence available: two block this agent by
     name in robots.txt (decisive), one is unreachable, and the only robots-permitted candidate
     answers non-browser clients with 403.
  2. Writing a template for 91mobiles anyway would be inventing a URL shape that has not been shown to
     resolve — precisely the mistake DS-1 refused when it declined to write
     `pricehistoryapp.com/product/{slug}`. Its 403s do not even prove the slug pattern is right.

This is the bead's **expected, acceptable outcome**, not a failure: the `offsite` seam built in beads
02/03 is correct and simply never fires. `trust_assessment.offsite` stays `null`, `rating_disagrees`
never fires from an off-site source, and cross-marketplace corroboration via `product_key` (bead 02)
carries R3's "beyond the site" half on its own — with zero new hosts, which is why R5's residual is
unchanged.

WHAT SHIPPED INSTEAD: the `kind: "review"` adapter slot itself, so a source that later qualifies is a
**data change** (`sites/<review-site>.json`) with no code edit. `scripts/policy.js` gained the kind at
exactly four sites — `REQUIRED_URLS`, the kind check, the `kind !== 'shop'` capture block, and the
whole-set `covers` gate — so a `review` adapter inherits the non-empty-`covers` rule and the
adversarial-path rejection unchanged. The guard is unaffected: `policy.js` is its only import and
`node scripts/guard.js selftest` still prints **`selftest OK: 60 cases`**.

OPEN FOR THE HUMAN, alongside H6/H7: in a real browser pane, check 91mobiles' constructed lookup for
a real product — does it resolve, and does the rendered page expose a rating and a review count as
text with no click? If both hold, it qualifies and one data file ships; if either fails, "none
qualified" stands as final. Its robots.txt already permits it, so the only open questions are the URL
shape and the un-clicked text read.
